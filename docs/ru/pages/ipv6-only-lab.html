Создание сети IPv6-only с доступом к IPv4

Я хотел отдельную сеть, в которой не нужно предполагать наличие IPv4 у каждого устройства. Вместо простого отключения IPv4 на ноутбуке создал отдельный VLAN на реальных коммутаторах и точках доступа, с маршрутизацией IPv6, DHCPv6, DNS64 и NAT64 на шлюзе.

Начало с отдельной сети

Шлюз — мой обычный OPNsense, но VLAN41 выделен для лаборатории. Существующие домашние сети оставил без изменений, новый тег передал через три управляемых коммутатора к двум точкам UniFi Wi-Fi 7 и uplink Proxmox. Тестовый SSID использует отдельный VLAN, а не конфигурацию основного корпоративного Wi-Fi.

В этом VLAN нет IPv4-адреса, шлюза и DHCPv4. Windows может самостоятельно назначить link-local IPv4-адрес, но это не даёт ей IPv4-маршрута в интернет.

Лаборатория в общих чертах

Шлюз OPNsense IPv6-only Router Advertisements · Kea DHCPv6 · DNS64 и Tayga NAT64
Управляемый VLAN41 Тегированный через три коммутатора

UniFi Wi-Fi 7

Две тестовые точки доступа. Windows и Android испытаны с нативным IPv6 и NAT64.

Uplink Proxmox

Тег VLAN доступен лаборатории. Делегирование префикса и клиенты за виртуальным маршрутизатором ещё не испытаны.

Упрощённое публичное представление испытанной сети, не физическая карта портов.

Android оказался полезным для сравнения с Windows. Он получил глобальный адрес через SLAAC без необходимости stateful DHCPv6-адреса, выданного Windows. Оба имели нативный IPv6. Для сайтов только с IPv4 DNS64 и NAT64 обеспечивали доступ без добавления IPv4 в клиентскую сеть.

Важные испытания

На Windows-ноутбуке проверил router advertisements, назначенные IPv6-адреса, нативную IPv6-связность и адрес из префикса NAT64. Android-телефон в том же тестовом Wi-Fi также открывал нативные IPv6- и IPv4-only сайты. Проверил доступ из обычной Core-сети к ноутбуку в лаборатории, включая успешный RDP после добавления узкого локального правила Windows Firewall. Доменную GPO для этого не менял.

По пути встретились вводящие в заблуждение симптомы. Один сайт проверки IPv6 имел собственную проблему с сертификатом, что не свидетельствовало о дефекте VLAN. При ранней диагностике один раз перезагрузил шлюз, но не могу утверждать, что перезагрузка решила проблему. Проверенное поведение клиентов отделяю от предположений о первоначальном сбое.

Что ещё не проверено

Uplink Proxmox передаёт тег VLAN, а Kea имеет пул префиксов для будущих виртуальных маршрутизаторов. Я ещё не подтвердил получение делегированного префикса виртуальным firewall, маршрутизацию в отдельный LAN и прохождение реального клиентского трафика за ним. Это следующий существенный тест.

Правила разделения LAB и Core, Guest и LAB загружены, но полный набор независимых негативных тестов с обеих сторон не зафиксирован. Подготовил временное WAN-правило для входящего IPv6-теста, но оставил его отключённым. Не пробовал подключение из публичного интернета и не проверял окончательный порядок действующих правил после сохранения в GUI.

Делегированный префикс провайдера тоже может изменяться. Ещё нужно наблюдать поведение лаборатории в этом случае, включая алиасы и клиентов.

Что хочу попробовать дальше

Для IPv6-only экспериментов готова отдельная VM OPNsense, но новое подключение WAN и DHCPv6 prefix delegation требуют проверки конфигурации. Вернувшись к тесту, начну с делегированного префикса и downstream LAN, затем проверю нативный IPv6, DNS64/NAT64 и пути, которые должны оставаться закрытыми. Рабочие сети не участвуют в эксперименте.
