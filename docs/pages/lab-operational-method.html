How I Test Firewalls in Proxmox

When I install a new firewall, I don't try every feature at once. I start with a working WAN and LAN connection, test it from a client and build on that. Repeating the same steps makes it easier to spot what is different between products.

The first round of tests

  1. Boot and management: check the initial interfaces, how to reach the UI or CLI and whether management access is limited to the lab.
  2. WAN: confirm DHCP or static addressing on the intended upstream, then check DNS and outbound connectivity.
  3. LAN: connect a Windows or Linux VM, check DHCP/DNS and establish the default route.
  4. NAT and forwarding: check outbound connections, then use a selected RDP or service port forward as a simple inbound test.
  5. Policy: try traffic that should succeed and traffic that should be blocked. These negative checks are not complete for every platform yet.
  6. Recovery: record what changes after restarting the firewall or restoring a snapshot, rather than assuming its runtime state is permanent.

What caused trouble

An early DHCP problem in the lab WAN needed tests at the switch, gateway, Linux bridge and guest NIC. During the IPFire setup, the WAN was initially attached to the wrong virtual bridge. Storage health and KDE graphics problems also turned into their own investigations.

One lesson has been to distinguish basic network separation from full security isolation. Different Linux bridges make a useful lab layout, but I still need to test IPv4 and IPv6 paths toward all protected services.

My November 2026 DD-WRT test added another important check: successful NAT is not enough if the guest cannot reboot cleanly. I traced a kernel panic to stale GRUB parameters regenerated from a binary template; a corrected UEFI reboot path passed two guest restarts. Testing with a real Ethernet laptop

I now use a dedicated physical lab port to connect an external laptop to the selected firewall's virtual LAN. The Proxmox hookscript removes the connection when two or more firewall VMs run; I tested this with both two and three guests. I also checked internet and RDP forwarding for all eleven platforms with the laptop path available. That is not a substitute for negative-path isolation tests.

Future test environment

I now have an IPv6-only upstream working with physical Windows and Android Wi-Fi clients. Prefix delegation to a virtual firewall is still open. I also want a separate physical test access point for PacketFence, EAP-TLS and other NAC experiments without changing my normal enterprise Wi-Fi. Commercial firewall evaluations are also on the roadmap, subject to trial and licensing conditions.
