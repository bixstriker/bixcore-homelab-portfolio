BiX Barox Config Tool

Working with managed switches made me want something more useful than a collection of copied CLI commands. I started building a tool that can read configuration exports, help me understand what is configured, and prepare documented recovery steps. It gradually grew into a parser, an analysis engine, a Windows GUI and a separate line of CLI research.

Where the idea came from

In electronic security and video-surveillance projects, a switch can be a critical part of the installation. VLANs, uplinks, multicast, management access and other settings can affect the whole system. Rebuilding a configuration manually from a saved export is not something I want to do by guesswork.

My initial goal was practical: take a Barox running or startup configuration and produce an ordered CLI procedure with explanations that an engineer can review and apply manually. Later, I added tools for comparing configurations and highlighting findings across switches that belong to the same network.

What the tool does today

Configuration to CLI

Reads exported configurations and creates an ordered list of CLI steps, a human-readable restoration guide and a structured plan. It keeps source references and flags commands it cannot validate instead of pretending to know their meaning.

Configuration analysis

Checks a single switch for local findings and compliance rules. With multiple exports from the same system, it also performs cross-switch analysis. Reports can be presented in English, German or Russian.

Windows application

A small desktop GUI lets me select or drag in exported files, choose a report language and generate outputs. It is a front end for the offline conversion and comparison functions, not an automatic switch configuration tool.

CLI and hardware research

I built a separate research workflow for collecting and reconciling command syntax from firmware material and live device help. I also tested selected serial-console state transitions on hardware while working toward a controlled restoration workflow.

The more interesting engineering problems

CLI grammar is not the same as a tested command. For the main Barox reference model, my research catalog contains 6,644 context-and-syntax records across eight CLI contexts. Some records come from live help, while others have only firmware or combined evidence. That count is not a claim that 6,644 commands were executed successfully on a physical switch.

Comparing switches requires context. For example, identical IP addresses do not mean the same thing across different VLANs, and an unknown uplink is not proof that no cable exists. I had to distinguish observed facts, configured state, inferred relationships and policies that belong to a specific installation.

A safe restore needs more than command generation. A serial session has prompts, modes, fragmented replies and possible command errors. I tested selected transitions, timeouts and prompt handling on hardware, but automatic application, verification and recovery from failures remain separate unfinished work.

Testing and limitations

The repository documents 515 discovered regression test cases, with an earlier successful full run reported during development. I haven't treated that historical report as a fresh run or as proof of full hardware compatibility. Selected console tests have preserved hardware evidence, but the newer documentation work did not involve another physical-device session.

The application is still a personal engineering project. I do not treat firmware syntax as automatic authorization to apply a command, assume every Barox model behaves identically, or claim that all generated restoration steps are safe to execute without review. General automated restore and remediation are still future work.

Why the source code isn't public here

The development repository also contains research artifacts, device captures and generated configuration/restore material. Some of those can reflect real installations or contain sensitive settings. Rather than publishing the complete archive, I've kept it private and written this public, sanitized project overview. It includes no customer configurations, device addresses, credentials, or raw management transcripts.
