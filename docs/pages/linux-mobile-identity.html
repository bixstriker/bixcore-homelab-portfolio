KUBUNTU / ANDROID / SCEP

Linux and Android on the Same PKI

Getting certificate-based network access working on Windows was only part of the project. I also wanted Kubuntu and Android devices to join the same enterprise Wi-Fi without sharing a password, and each platform needed a different enrollment approach.

Kubuntu and Active Directory

I joined a Kubuntu workstation to the domain using realmd, SSSD and Kerberos, then checked domain account and group resolution. Wired and wireless NetworkManager profiles use managed EAP-TLS client certificates. I also set up certificate renewal automation and tested the resulting connection behavior.

I kept a separate local administrator account so that a directory or network problem wouldn't leave me without a recovery path. The Linux setup also has its own login-session and WireGuard integration notes.

Dual boot and remote access on Kubuntu

On a physical Windows/Kubuntu laptop I kept GRUB first in the UEFI boot order but configured Windows as its default. A real reboot confirmed the menu and default choice.

KRDP initially accepted an RDP/TLS connection but then showed a black screen and disconnected. A saved Windows RDP connection that passed the complete Linux UPN with the correct account context worked. I renewed KRDP's separate self-signed TLS certificate and tested Ed25519 SSH key login from Windows. These are remote-access credentials, not the Wi-Fi EAP-TLS client identity.

Android and managed certificates

For Android, I used mobile device management with SCEP enrollment through the internal NDES service. The managed profile installs the relevant trust material and a client identity, which Android can then use for EAP-TLS Wi-Fi. I tested that on multiple devices, including work-profile scenarios.

One surprise was that applying the Wi-Fi configuration could trigger another SCEP request. I investigated that as part of the profile workflow rather than assuming Wi-Fi authentication was broken. The devices connected successfully.

Recovering Android enrollment after a software update

After a Xiaomi tablet's Android/HyperOS update, the management agent reported that the SCEP server was unreachable. The enrollment endpoint still answered, and a second Xiaomi phone using the same profile received a new certificate and connected. I therefore investigated the managed work profile before changing NDES or the CA.

On 25 November I removed only the affected work profile, rebooted and enrolled it again, assigning the SCEP certificate profile before the Wi-Fi profile. The tablet and a second affected phone both recovered EAP-TLS connectivity. The CA issued new certificates, the superseded certificates were revoked and the CRL was republished. The devices' personal profiles and data were not removed.

The procedure worked, but I have not established the precise Android or management-agent defect. I did not need to modify NDES, FreeRADIUS or the certificate template.

Renewal and cleanup

On Kubuntu, I have a documented certificate renewal process. I tested one Android SCEP replacement through revocation of its old certificate and publication of the updated CRL. More renewal and recovery scenarios remain open.

The Proxmox host has its own Active Directory and HTTPS integration; I cover that under the virtualization setup rather than mixing it into the workstation enrollment story.
