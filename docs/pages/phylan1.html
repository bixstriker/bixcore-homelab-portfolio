PhyLan1: A Physical Client for the Firewall Lab

I wanted to test each virtual firewall with a real laptop over Ethernet, without adding a physical NIC to every VM or changing each guest's network setup. I made the Proxmox host switch one dedicated test port between the existing virtual LANs.

How it works

The host's dedicated test NIC belongs to a Linux bridge with no host IP address or gateway. A temporary virtual Ethernet pair joins that bridge to the LAN bridge of the selected firewall. The firewall's upstream remains on the isolated lab VLAN behind my main OPNsense gateway.

The laptop receives its network settings from whichever firewall is active. No extra NIC or bridge is installed inside any firewall VM.

One firewall at a time

Running firewall VMsPhysical test port
ZeroNo connection to a guest LAN
Exactly oneConnected to that firewall's existing LAN bridge
Two or threeDisconnected from all guest LANs

The Proxmox hookscript reacts to normal VM start and stop events and uses a lock so two events cannot rearrange the bridge at the same time. I didn't need to modify MikroTik, pfSense, Sophos or any of the other guests for this.

What I checked on 6 November

I tested the external Ethernet laptop with all eleven firewall/router platforms, and confirmed internet access and RDP forwarding to the reusable Windows and Linux clients in the same round of tests. These are user-confirmed end-to-end results, not a new packet capture for every platform. The OPNsense full clone and OpenFW added on 9 November were not part of this tested set, and I haven't added them to the host switching hook.

I also checked a changeover between two guests, the start of a second guest, and three firewall VMs running together. The port disconnected when more than one firewall was active and reconnected after only one remained.

Limits I haven't solved yet

This protects the physical port during normal Proxmox events; it isn't a complete network-isolation audit. There is no watchdog yet for a VM process that exits without its normal stop hook. The port should only be connected directly to the test laptop or to a dedicated, isolated access point — never to my regular home switch, where guest DHCP servers would cause trouble.
