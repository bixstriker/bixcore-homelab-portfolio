TACACS+ for Switch Administration

I wanted to use directory accounts for managing my switches, while keeping administrative privileges and recovery access under control. The interesting part turned out to be what happened when the TACACS+ service was unavailable.

How I put it together

I already use RADIUS and certificates for network clients, but switch administrator login is a different kind of access. I deployed tac_plus-ng using TACACS-NG-UI on my NAS. The backend uses validated LDAPS connections to two Active Directory controllers, with a separate web frontend and PostgreSQL database. I kept the existing reverse proxy for the UI.

I set up a simple distinction between an administrator with configuration access and other authenticated users with restricted privileges. Omada and Barox interpret privilege levels differently, so I tested actual access in each interface rather than assuming the numbers mapped directly.

Authentication and restricted roles worked on both switches. Authentication, authorization and accounting are configured where supported, but I have not audited every possible command or accounting record.

A controlled fallback test

Then I deliberately took the TACACS+ daemon out of service and tested whether the switches really allowed emergency local login.

  • Barox: the separate local administrator could sign in when TACACS+ was unavailable. Normal domain login resumed when the service came back.
  • Omada: local web login worked when explicitly set to local authentication. With TACACS+-then-local selected and the server unreachable, the same local account was rejected. I saw a similar symptom over SSH.
  • Network check: packet capture showed repeated TCP connection attempts from Omada with no reply. A targeted network drop reproduced the result without stopping the whole container stack.

The Omada failure is reproducible in my tested configuration. That does not prove the underlying cause is a firmware bug; I cannot see the switch's internal fallback decision. I sent the observations to TP-Link support on 12 November 2026, and I still consider this open.

Resource use and recovery

The Docker project separates the TACACS+ backend, UI and database. I also reduced the FastAPI service to one Uvicorn worker. A point-in-time measurement showed roughly 122 MiB for the running stack; it was not a peak-load test.

A central login service makes daily administration easier, but it also creates a dependency. I still need to document and test an independent database/configuration restore, and I won't count on the Omada local fallback until its behavior is resolved.
