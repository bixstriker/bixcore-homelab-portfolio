Certificate-Based Network Access

I wanted wired and Wi-Fi clients to use individual certificates instead of a shared network password. Getting that to work meant dealing with enrollment, trusted CAs, revocation and directory-backed authorization.

How the pieces fit together

Windows Server provides Active Directory and an enterprise certification authority. NDES handles SCEP for supported Android devices. FreeRADIUS runs on OPNsense and checks the client certificate before applying the relevant access policy at the switch or wireless access point.

Protecting the RADIUS transport too

I later added RadSecProxy in front of FreeRADIUS for both UniFi APs and the wired Omada switch. Transport mTLS and client EAP-TLS are two different certificate checks. The network devices use TLS 1.3 to reach the gateway, but the end-user EAP-TLS identities, directory authorization and CRL checks remain part of FreeRADIUS.

The switch needed a Let's Encrypt server trust chain and a separate local CA for its own client certificate. I kept its server-certificate verification enabled and tested new authentication and Accounting. The RadSec certificate and migration story →

What I have tested

  • Certificate enrollment and wired EAP-TLS for selected Windows machines.
  • Wired and Wi-Fi certificate authentication on Kubuntu.
  • Android MDM profiles issuing SCEP identities and using them for enterprise Wi-Fi.
  • Revocation-list publication and selected certificate-validation checks.
  • LDAPS directory lookup using the second controller while the first was unavailable.
  • A separate wired certificate/authorization design for the domain controllers, avoiding a bootstrap dependency on their own directory service.

What I learned from RADIUS Accounting and Disconnect

On 7 November I enabled Accounting for both UniFi access points while keeping my existing OPNsense FreeRADIUS service and certificate checks. The server already recorded switch sessions; after the UniFi change I could also see live Start and Interim-Update information for Wi-Fi sessions in its local database.

My first attempt to disconnect one phone's session failed with a NAK. It wasn't a failed EAP-TLS certificate: I had used the ID of an old session that ended when the phone roamed. I checked the newer Accounting record, sent a targeted Disconnect-Request for the current session and got an ACK. The phone visibly left Wi-Fi and connected again using EAP-TLS.

That proves targeted session termination and reauthentication for this test. That Disconnect test did not change the VLAN. I later tried a CoA VLAN request; the AP returned an Unsupported-Attribute NAK. The session-ID mistake →

Checking the authorization, not just the certificate

I tightened FreeRADIUS authorization and tested real phones. Disabling a local identity caused an Access-Reject at its next full EAP-TLS login; enabling it allowed access again. A mismatched EAP identity and a valid certificate with no matching permitted local record were also refused on new logins.

My RADIUS Control tool can target a UniFi session for reauthentication or Disconnect. I found that PMKSA cleanup did not clear the separate 802.11r fast-transition keys, so I don't describe account disabling as an instant guarantee that every cached Wi-Fi key has vanished.

I also attempted a live VLAN reassignment through CoA. The AP returned an Unsupported-Attribute NAK, not a working VLAN change. How I built RADIUS Control →

Managing wired sessions without touching the directory

I extended my RADIUS Control tool to individual Omada wired 802.1X sessions. The gateway checks the live client and port, and an old Accounting row is closed only after a verified ACK and a matching new session. I tested it on separate workstation and domain-controller ports.

This does not turn RADIUS Control into an AD administration tool: it does not disable domain accounts, change directory rights or edit EAP-TLS certificates. The completed RADIUS Control project →

Problems and the next stage

The trickiest parts were getting a domain controller through its own protected switch port, proving LDAPS fallback and understanding extra SCEP enrollment requests from Android.

Now I want to make the certificate lifecycle more predictable: renewals, revocation of old device identities and recovery of the CA itself. The second domain controller helps directory queries, but it doesn't replace that work.
