Building an IPv6-only Network That Can Still Reach IPv4

I wanted an isolated network where I could stop assuming that every device had IPv4. Rather than disabling IPv4 on a laptop and calling it done, I built a separate VLAN through my real switches and access points, with IPv6 routing, DHCPv6, DNS64 and NAT64 at the gateway.

Starting with a separate network

The gateway is my regular OPNsense appliance, but VLAN41 is a dedicated laboratory segment. I left the existing home networks alone and carried the new tag across three managed switches to two UniFi Wi-Fi 7 access points and the Proxmox uplink. The test SSID uses the isolated VLAN; it doesn't reuse the main enterprise Wi-Fi configuration.

There's no IPv4 address, gateway or DHCPv4 service on this VLAN. A Windows client may still generate a link-local IPv4 address for itself, but that doesn't give it an IPv4 route to the internet.

Android was a useful contrast to Windows. It obtained a global address through SLAAC and didn't need the stateful DHCPv6 address Windows received. Both had native IPv6 connectivity. When a website was available only over IPv4, DNS64 and NAT64 made the connection possible without adding IPv4 to the client network.

The tests that mattered

On the Windows laptop I checked router advertisements, assigned IPv6 addresses, native IPv6 connectivity and an address in the NAT64 translation prefix. An Android phone on the same test Wi-Fi could open native IPv6 and IPv4-only sites too. I also tested access from the regular core network to the laptop in the lab, including a successful RDP session after adding a narrowly scoped local Windows Firewall rule. I did not change the domain GPO for that test.

I also found a couple of misleading symptoms along the way. A site I used to check IPv6 had its own certificate problem; that wasn't evidence of a broken VLAN. I rebooted the gateway once while investigating early connectivity, but can't say the reboot itself fixed the problem. I kept the verified client behavior separate from guesses about the original failure.

What I deliberately haven't claimed

The Proxmox uplink carries the VLAN tag, and Kea has a configured pool of prefixes for future virtual routers. I haven't yet shown a virtual firewall obtaining a delegated prefix, routing it to a separate LAN and passing real client traffic behind that LAN. That's the next meaningful test.

The firewall rules for LAB-to-Core and Guest-to-LAB separation are loaded, but I have not recorded the full set of independent negative-path tests from clients on both sides. A temporary inbound-IPv6 test option was prepared in the WAN interface; it stays disabled by default, and no successful inbound test from the public internet has been recorded. I won't treat a saved GUI rule as proof of its final runtime order.

Finally, the provider's delegated prefix is dynamic. The lab uses a current prefix and some local aliases need to be checked and updated if that delegation changes. I haven't observed a real renumbering event since creating this VLAN, so I can't claim that the whole chain recovers automatically.

What I want to try next

I have a separate OPNsense VM ready for IPv6-only experiments, but its new WAN connection and DHCPv6 prefix delegation still need a fresh configuration check. When I return to that test, I'll start with the delegated prefix and downstream LAN, then verify native IPv6, DNS64/NAT64 and the paths that should remain blocked. The existing production networks are not part of that experiment.
