Building My Own RADIUS Session Management Tool

I wanted to manage one network session without guessing which device was connected. What started as a small Accounting viewer became my own working tool for Wi-Fi, wired 802.1X and guest access.

From one stale session to a stable release

My first attempt to disconnect a roaming phone used an old RADIUS Session ID and failed. I was switching between the UniFi controller, FreeRADIUS Accounting and OPNsense to find out what was actually connected. That experience gave me a concrete reason to build BiXCore RADIUS Control.

I finished stable v1.0.0 on 19 November 2026 and deployed v1.0.1 later that day with a more usable phone and tablet layout. The tool runs on my NAS and works with the existing FreeRADIUS service on OPNsense. It is not a replacement RADIUS server.

What I use it for

The interface shows fresh, stale and ended RADIUS Accounting sessions, recent history, local FreeRADIUS accounts and personal Captive Portal sessions. I can refresh the data and check the current session before taking action.

I can manually enable or disable local FreeRADIUS accounts and change their configured VLAN. Those changes apply to future authentications; they do not instantly move an existing Wi-Fi connection. I also manage personal portal access and a separate shared guest Wi-Fi account, with explicit confirmation for guest Disconnect.

Domain accounts are different: I can see their sessions and, where supported, disconnect one device, but I cannot disable AD users, alter directory permissions or change their VLAN from this tool.

Three containers instead of an overpowered web app

I moved the production application into three Docker services. web serves an authenticated FastAPI interface with four languages, light/dark themes and an action history. sync regularly imports a sanitized gateway snapshot. control handles narrowly approved changes. The browser-facing container does not hold general SSH access or unrestricted OPNsense credentials.

Restricted gateway helpers check the live target again before each change. The permanent audit log records ACK, NAK, errors and refused actions. I made sensitive operations fail closed if the audit store is unavailable: I would rather see an error than lose the record of what happened.

Testing UniFi on real phones

A targeted online RADIUS Disconnect returned an ACK, and the phone disconnected and completed EAP-TLS again. EAPOL reauthentication also worked. For an already ended connection I could examine and clear selected leftover PMKSA state rather than pretend it was still online.

I tightened FreeRADIUS authorization separately. In live tests a disabled local identity was rejected at its next full EAP-TLS login, and it could log in again after being enabled. A mismatched EAP identity and a certificate without a permitted matching local account also failed new logins. One personal guest portal account was denied a second simultaneous session.

I tried live VLAN reassignment through UniFi CoA as well. The AP returned an Unsupported-Attribute NAK; I have not claimed that as a working feature.

Omada taught me not to trust an ACK alone

Wired 802.1X on my Omada switch needed its own implementation. My early request produced a NAK. After I narrowed the RADIUS packet to the fields the switch accepted, the switch returned a verified Disconnect-ACK.

But there was another trap: the switch did not always send an Accounting-Stop for the old session. Once, the new Accounting-Start arrived just after my original timeout. Closing the old row on ACK alone could have left misleading history, or worse, targeted the wrong record.

I changed the cleanup so it happens only after a verified ACK and a unique replacement Accounting-Start for the same client and port, while the old database row remains unchanged. There is a bounded wait and no automatic retry for an uncertain result. I tested the resulting behavior on two physical switch ports, with a workstation and a domain controller. Both had the expected new session and a correctly closed old record.

The action is restricted to eligible individual wired 802.1X sessions on the configured Omada switch. It is not a blanket switch-port shutdown. The Omada failure and fix →

The Wi-Fi keys I decided not to flush

I found that PMKSA cleanup did not remove separate 802.11r fast-transition keys on the UniFi APs. A disabled identity is rejected at its next full EAP-TLS authentication, but an existing cached FT context may remain. I accepted that limitation for my personal network rather than doing disruptive global cache flushes.

I also captured a TLS 1.2 client offering an old session ID while FreeRADIUS performed a complete handshake. The full authentications took around 0.16–0.27 seconds in those samples. I left persistent TLS session caching off; the possible gain wasn't worth adding another edge case to authorization.

What the release tests cover

The deployed v1.0.1 interface, three healthy containers and access-control checks passed. The release suite recorded 257 Python tests passed, one skipped. Browser layout tests covered phone, tablet and desktop widths, themes and languages using a mock API; they did not send new live Disconnect commands. Live UniFi and Omada operations were checked separately.

The software is finished, but one infrastructure maintenance task remains: the dual-interface NAS route used to reach OPNsense has not yet been verified across a full NAS reboot. A successful container restart is not the same as end-to-end boot recovery.

I keep the source and live configuration private. This page is about what I built, where it failed and what I actually checked.
