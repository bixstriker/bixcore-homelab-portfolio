VIRTUAL FIREWALLS / REAL CLIENT TESTS

The Virtual Firewall Lab

My Proxmox lab lets me work with firewall systems without replacing the OPNsense gateway I use every day. I can build a configuration, connect a Windows or Linux client, test the traffic and then move on to another platform.

How the lab works

Proxmox runs on a reused desktop with Debian 13. I have a dedicated upstream for the test firewalls and separate Linux bridges for their LAN interfaces. The same client VMs can be attached to the firewall being tested, so I don't need a large number of machines running at the same time.

As of 9 November 2026 the lab contains 18 VMs: thirteen router/firewall instances, two reusable Windows/Linux clients, PacketFence NAC, OpenWISP and Taranac. The router/firewall instances cover twelve different platforms, including two independent virtual OPNsense guests. In addition to MikroTik CHR, pfSense CE, Sophos Firewall Home, VyOS, FortiGate VM, OpenWrt and IPFire, I installed NethSecurity 8.8, FreeSense 1.1.11, DD-WRT r66445 and a separate OPNsense Community 26.7 guest. Each firewall has its own virtual LAN, connected only when needed to the shared test clients. I verified basic management, IPv4 connectivity, DHCP, NAT and selected RDP forwards with the four new systems. I have also tested an external laptop over the dedicated PhyLan1 Ethernet port with all eleven router/firewall guests. A Proxmox hookscript connects that port only when exactly one of those guests is running. The new OPNsense clone and OpenFW were not part of those eleven PhyLan1 tests; full negative-path and performance testing remains open.

The new PacketFence VM is not one of the eleven firewalls and does not use PhyLan1. I tested virtual guest registration, access revocation and recovery after fixing separate IPSet and DNS problems. The physical test-port design has its own write-up.

Four additional guests on 9 November

I installed OpenWISP 26.09.2 on a small Debian server and confirmed that its Docker services were running, HTTPS was reachable and I could sign into the dashboard. I also installed Taranac Community Edition 1.3.3 and checked its initial setup and WebGUI login. Neither has yet gone through a full RADIUS, NAC or network-management exercise.

I made a full disk clone of the lab OPNsense guest for future IPv6-only tests. Its virtual disks are independent, but some guest settings were copied as well. I still need to confirm its new NIC attachments before trying DHCPv6 prefix delegation, and I won't start it alongside its source while they might share an internal LAN.

OpenFW UTM Community 4.2.1 is the other new firewall. I checked its LAN DHCP, management interface and a real RDP connection through a WAN-side forwarding rule to the Windows test VM. I haven't completed SSH login or a full policy review; enabling broad management listeners during setup is not a permanent security baseline.

Problems I encountered

The VLAN path for the lab WAN caused a DHCP investigation that went all the way from the gateway to the physical switch and the virtual NIC. I also corrected an upstream bridge mistake during the IPFire setup. Those are described in the troubleshooting notes. More recently, DD-WRT required an unusual UEFI boot repair: the wrong root partition and filesystem were embedded not only in GRUB configuration but also in a binary configuration template. Correcting the template and the UEFI reboot parameter gave two successful restarts. The boot case and an SSH blocklist incident are documented separately; DD-WRT shutdown is still not solved.

RADIUS, 802.1X and NAC

The real network already uses FreeRADIUS with certificate-based access. In the lab I want to test how firewall and access-control systems interact with RADIUS, and later connect that work to PacketFence. PacketFence's first isolated virtual guest/captive-portal tests already work, but RADIUS and 802.1X are still open.

Real Wi-Fi clients

A dedicated Cudy Wi-Fi 7 access point would let me try captive portals, VLANs, EAP-TLS and guest isolation with physical devices, without changing the main Wi-Fi setup.

IPv6-only and routing protocols

The IPv6-only upstream now works with physical Wi-Fi clients and is carried to Proxmox. I still need to test it with a virtual router, get a delegated /64 and route traffic through a separate guest LAN. BGP and FRR experiments remain on my list.

The common test checklist →

Before comparing products, I want to check unwanted access paths, management exposure, restarts and configuration recovery. A simple successful RDP port forward is a useful first test, not the end of the assessment.
