ROUTERS / FIREWALLS / PROXMOX

Firewall and Router Systems I've Tried

I use the same virtual Windows and Linux clients to get a feel for different firewall systems. My first goal with each product is simple: set up the WAN and LAN correctly, make client traffic work, then find out how its firewall rules and administration behave.

The common lab setup

Each firewall VM has a dedicated test upstream and its own virtual client network. I normally run one firewall with one or two clients, rather than all the products together. None of these experiments replaces my everyday OPNsense gateway.

FreeSense boot incident →

My 6 November updates included MikroTik CHR on RouterOS 7.25.1, Sophos Firewall Home on SFOS 23.0 GA, and IPFire Core Update 205. I left DD-WRT on its tested build because its local boot fixes may not survive a firmware change. I haven't treated a GUI showing “no updates available” as proof of an exact build number.

I also tested the internet path, selected RDP forwarding and an external Ethernet laptop across the original eleven firewall/router VMs. The PhyLan1 setup made that last check possible without rewiring guest NICs. Those checks don't cover every VPN, IPS or 802.1X feature.

As of 9 November there are thirteen firewall/router VMs, but only twelve distinct platforms: the extra OPNsense VM is a full clone for the still-unfinished IPv6-only WAN and prefix-delegation experiment. The original two-VM OPNsense setup isn't proof that both copies can safely share their inherited LAN settings.

DD-WRT: the bootloader needed more than one fix

After a reset, the DD-WRT guest entered a kernel panic because the boot configuration still referred to an outdated disk name and filesystem type. I found the ext4 root partition, corrected the boot parameters, and discovered that DD-WRT could regenerate GRUB settings from a compiled template inside its service executable. I updated both the generated configuration and the template with size-preserving substitutions, keeping a recovery snapshot. Changing the kernel reboot method to UEFI fixed the guest restart hang. Two subsequent reboots worked; normal ACPI shutdown is still unresolved.

An unrelated SSH/WebGUI access failure turned out to be the guest's brute-force protection blocking the administrator after failed SSH attempts, not a network bridge problem. I checked the blocklist and filter rules before restoring the lab management path. Read the boot incident or the management-access case. The reboot problem is documented separately.

What the tests taught me

Most of the early problems were about getting packets through the right interface. A virtual NIC connected to the wrong bridge can look like a DHCP or firewall problem, so I now check the host, switch and gateway before changing guest rules.

Port forwarding is a useful way to verify a path, but it doesn't say much about what a firewall blocks. I want to make the next round more consistent: positive and negative access tests, IPv4 and IPv6, management security, restart behavior and eventually performance.
