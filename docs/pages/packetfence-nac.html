PacketFence: My First NAC Lab

I wanted to see what a NAC system actually does when a client registers through a portal, and what happens when I take its access away. Getting a Windows VM registered was easy compared with getting the policy to work.

The setup

I installed PacketFence 15.2 on Debian 12 in a separate Proxmox VM. It has an isolated IPv4 upstream and its own virtual client network with DHCP, DNS proxy, inline filtering, NAT and a captive portal. I started with a guest registration using a Null source, rather than attempting enterprise 802.1X immediately.

The test client was another Windows VM. No physical cable or access point has been connected to this PacketFence network yet.

A guest was registered, but could not browse

Windows found the portal and completed registration, but outside HTTPS still failed. PacketFence's IPSet service was rejecting a generated entry: the registered-client set expected an IP address, but the rule contained an IP-and-MAC pair.

I investigated the rule generation with Codex and applied a narrowly scoped local hotfix. It kept the original deny-by-default approach rather than adding a bypass rule. The format problem is also discussed in upstream issue #9339. My installed build was not assumed to contain the upstream fix.

Then DNS pointed everything back to the portal

Once the IPSet service worked, TCP connections to external addresses succeeded, but normal website names kept resolving to the captive portal. The DNS proxy was forwarding queries back to its own listening address. I changed the upstream to the lab gateway while keeping PacketFence as the resolver for clients.

With those two problems addressed, the Windows guest resolved public names and completed an HTTPS request with normal certificate validation.

What I tested

ActionResult
Guest registeredExternal TCP/443 and HTTPS browsing worked.
Registration revokedA new external connection was blocked and the portal appeared again.
Guest registered againAccess returned automatically, without manually editing IPSet.
PacketFence VM rebootedIPSet, DNS and DHCP services recovered; guest membership, name resolution and HTTPS worked again.

The admin proxy eventually became active after reboot, but I did not record a fresh GUI login. The full revoke-and-register cycle was rerun after the backport, but not as a separate test after that reboot.

Replacing the temporary fix with an upstream backport

On 9 November I revisited the IPSet error rather than leaving my first one-line workaround in place. PacketFence's merged PR #9350 addressed more than the original IP/MAC mismatch, so I brought its relevant logic into the installed 15.2.0 module as a local functional backport. I checked the candidate against the upstream change, ran the Perl syntax check and kept a rollback copy before restarting only the affected IPSet service.

A running daemon wasn't enough proof. I checked that the active guest was present in both the registered and guest sets, removed its registration and watched the connection fail and the captive portal return. Re-registering it restored access. After a normal VM reboot, the DHCP, DNS, IPSet and admin-proxy services were active, the guest's set membership was still there and websites opened without another registration.

This is not the same as installing a new official PacketFence package. A later upgrade might replace the locally modified module. The backport also says nothing by itself about RADIUS Accounting, 802.1X, MAC/IP spoofing or Security Events.

What comes next

The working functional backport can still be overwritten by an update. I need to check the next maintenance build for the upstream change and rerun registration, revocation and reboot tests after upgrading. RADIUS, EAP-TLS/802.1X, VLAN assignment, isolation actions and physical clients are separate planned experiments, not achievements of this session.
